### 关键排坑记录（dulwich 1.2.17 实际行为与常见假设不同）
1. `porcelain.status().staged` 返回 `{'add': [], 'delete': [], 'modify': []}`，**空时字典仍为真值**，
   直接用 `if st.staged:` 判断工作区是否脏会永远成立。必须归一化为 `{path: kind}`。
   → 封装 `_normalize_staged()` / `_normalize_paths()`。
2. `porcelain.reset()` 没有 `paths` 参数，无法做选择性取消暂存。
   → 改为手工操作 index：`Tree.lookup_path(store.__getitem__, key)` 取 HEAD blob，
   写入 `IndexEntry(0,0,0,0,mode,0,0,0,sha)`（**统计字段必须清零**，
   否则 dulwich 按 stat 快速比对会把"已修改"误判为"未变化"）。
3. `porcelain.checkout(repo, target, new_branch=...)` 要求 target 是已存在的 ref，
   新建分支应传 `target=b"HEAD"`。
4. 合并冲突后 `porcelain.reset(hard)` 会因索引含未合并条目抛 `UnmergedEntries`。
   → 改为**前置只读试合并** `porcelain.merge_tree(repo, base, ours, theirs)` 预判冲突，
   冲突则直接中止、不做任何改动（这正是需求 9 想要的行为）。
5. `dulwich.errors` 无 `UpdateRefsError`；有 `WorkingTreeModifiedError`。
6. PyInstaller 排除 `distutils` 会与 hook 冲突报 `ValueError: Target module "distutils" already imported`，不能排除。
7. **Qt 崩溃定位**：`QThread` 对象在底层线程真正结束前被 Python GC 回收 → 进程直接中止（退出码 127）。
   → TaskCenter 用 `finished` 信号 + 固定长度 graveyard deque 持有引用。
8. windowed 打包下 `sys.stderr is None`，`logging.StreamHandler` 会出问题 → 加判空。

### 需求

  `content.height()` 与 `minimumSizeHint()`、以及卡片/按钮的 `geometry()` 上下边关系。

- 新增 `ui/widgets.py::scrollable(widget)`：把表单型页签（概览）包进

  `QTabWidget::pane` 白底透上来，与其它页签一致；

  `enable_stop()`、`_set_bar_state()`；`finish(ok=False, cancelled=True)` 用动态属性
  `state=error|cancel` 把进度条换成红/灰（原先失败后仍显示满格蓝色，极易误判）；
- 结束后按钮退化为**「关闭」**并保持可用 → 满足「失败后也可停止/清理」；

### 本轮排坑
19. **测试里取到的几何是无效的**：`ReposPage` 未选中仓库时 `detail` 是隐藏的，
    控件几何全是残值（探针里 `tabs=transfer=480` 且按钮 `visible=False`），
    据此断言会得到「看起来像重叠」的假结果。→ 布局用例必须先用 `_register_path()`
    注册一个真实仓库并等 detail 可见，再量几何。
20. `bottom()` 是 `top + height - 1`，判断「不重叠」要用 `top2 > bottom1`
    （用 `>=` 会在仅 1px 间隔时误判为重叠）。
21. 离屏探针里 `os._exit(0)` 会丢掉缓冲输出（用 `-u` 也不行），
    且 `MainWindow` 的后台线程会让解释器不退出 → 探针要显式 flush 后再 `os._exit`。
22. 用真实项目目录做探针会**写入用户的 `GitDeskData/repos.json`** 并可能触发真实网络请求，
    探针一律先设 `GITDESK_DATA_DIR` 到临时目录 + 用临时仓库。
23. 面板「停止」按钮在页面上有双重处理：`TransferPanel._on_stop_clicked`（改按钮状态）
    与页面 `_on_stop_transfer`（真取消任务）。**测试按钮状态机要用独立的

## 第五轮需求：远程列表勾选多个远程（一次推送）

### 实现
- `remote_list` 由 2 列改 **3 列**：`["", "名称", "地址"]`，第 0 列是

## 第六轮需求：徽标「与远程一致」是跟哪个远程比（同步目标明确化）

### 起因
用户在 `D:\Git\photoWeb`（origin=gitee、github=github 两个远程）上问：
「与远程一致」是跟哪个仓库一致？

### 诊断（只读验证用户仓库）
- `.git/config`：`branch.main.remote = github` → 上游是 `refs/remotes/github/main`
- 判定链：`SyncState.sync_state()` → `_upstream_ref()` 读配置 → 比 `refs/heads/main` 与上游 ref
- 结论：只跟 **github** 比；origin(gitee) 不参与判定
- 发现的真实隐患：概览页「推送本地提交」走 `_primary_remote()`（origin 优先）且传
  `set_upstream=True` → 推 Gitee 却盯 GitHub，且会把上游改写成 origin，徽标比较对象随操作漂移

### 实现（用户选择「徽标标明远程名」）
- `gitengine.py`：新增纯函数 `upstream_remote_name()`（`_UPSTREAM_REMOTE_RE` 解析
  `refs/remotes/<name>/`）+ `SyncState.remote_name` property（非远程上游返回空串）
- `repos.py`：新增 `_sync_remote()`（**跟踪远程 → origin → 第一个**），
  `_credential()` / `_poll_remote()` 都改用它 → 获取 / 拉取 / 推送与徽标同源
- `_render_overview()` 徽标文案：「与 github 一致 / 领先 github 2 / 落后 origin 3 /
  与 github 已分叉」；上游非远程时回退「与上游一致」
- `do_push()`：`set_upstream = (目标远程 != 当前上游)` —— 推给上游时不再改写配置
- `do_push_selected()`：不再固定给 origin 设上游；有上游且推送到它 → 保持；
  从未建立上游且只推一个 → 才建立
- 新增 `_hint_default()` / `_hint_text(sync)`：概览提示写明「获取/拉取/推送都作用于「github」」；
  `_check_notice()` 的「远程有新提交」也带远程名
